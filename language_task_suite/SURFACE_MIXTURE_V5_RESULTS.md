# Joint narrative, place retrieval, and subject counting (v5)

`surface_mixture_v5.py` adds a **subject-count** task to the joint v4 narrative stream. It retains v3's competing verb and object rules and v4's object-to-place questions. A count question asks how many completed narrative sentences had a given person as the **main actor**; people in side clauses or earlier questions do not count. The wording was corrected from “mentioned,” which would have implied counting side-clause names. All next-token probabilities and answers are determined by the visible prefix.

Example from the generator: “At the store, Alice moves the heavy photograph before the visit. At the pier, Alice checks the complex photograph before the journey. How many times was Alice the main actor? Answer: 2.” A question is available only when observed people have different main-actor counts; its queried person is uniform among observed main actors. For a fixed history, at least two query names therefore have different correct answers. The count task is distinct from v4's object-to-place binding, while all tasks share the same narrative context and model parameters.

| Prediction site | Competing or required information | Decisive intervention |
|---|---|---|
| Narrative verb | Subject lexical proposal, cue, prior same-subject verb, previous place | Change a cue, prior verb, or place while preserving the other sources |
| Narrative object | Adjective proposal, cue, prior same-subject object, previous event | Change a prior object or event while preserving the current frame |
| Place answer | Queried object and its latest narrative place | Swap the query key or matching place; edit another object's place as control |
| Count answer | Queried person and number of narrative sentences where they are main actor | Swap the query name or a relevant historical subject; edit a place as control |

These are four labeled sites within one autoregressive stream, not four separate genre headers. The exact oracles support both training targets and independent held-out causal tests. Whole-family featurizer holdouts will require withholding *all* examples of one site during representation fitting, not merely changing surface phrasing.

`audit_surface_mixture_v5.py` replayed **216,000** prefixes in 3,000 streams of 72 tokens. It checked each sampled token's support, normalization, complete clause grammar, every narrative verb/object mixture against the standalone v3 oracle, and independent answers for both question types. At each count-answer slot it also checked the uniform query-name distribution and an alternative supported name with a different answer. All checks passed. The stream contained **11,402 verb**, **10,978 object**, **257 place-answer**, and **219 count-answer** slots. Count answers were split **114 one** versus **105 two-or-more**. The person names in side clauses are a deliberate nuisance for count questions, though their exact prevalence has not yet been measured.

The same frozen 480-window FineWeb panel still shows a large realism gap. In 72-token windows, synthetic versus FineWeb occurrence rates are **64.4% versus 69.0%** for newlines, **16.9% versus 12.7%** for question marks, **31.0% versus 20.4%** for colons, and **24.4% versus 41.5%** for digits. Quotes and parentheses remain absent in synthetic text, while FineWeb has them in **22.1%** and **20.6%** of windows. In 457 windows matched on their first 40 alphabetic words, repeated-word fractions remain **27.9% versus 16.6%**. These are form diagnostics, not evidence that natural text contains these task frequencies; the tokenizers also differ.

The model comparison uses three-layer, four-head, width-64 attention-only bilinear transformers with RMSNorm. Both train for 3,000 steps on the same seed and sampled stream with ordinary next-token CE plus exact-oracle expected CE at verb/object/place sites (weights **2/2/1**). One adds a count-site term of weight **1**; the other does not. Evaluation uses separate generator seeds. `eval_surface_mixture_v5_counts.py` reports count accuracy and KL for one versus two-or-more, compares against the exact best predictor that ignores the queried person, and measures three supported edits: change the queried person, change a prior main subject, and change a place that should have no effect on the count.

The corrected-wording run finished. On the separate 3,000-window seed-9101 panel it sees **194** count questions: **102** answer one and **92** answer two-or-more. The exact best query-blind predictor has **51.7%** accuracy and **.687** nats answer CE on those histories. The model has **52.1%** accuracy and **.760** nats CE, almost the same accuracy as that shortcut. It gets **91.2%** of one-count questions right but only **8.7%** of two-or-more. Its held-out seed-8101 count KL is **.725** nats. The paired edits make the failure unambiguous:

| Count edit | Supported pairs | Oracle effect TV | Model effect TV | Effect L1 error |
|---|---:|---:|---:|---:|
| Change queried person to one with a different count | 194 | 1 | **.0012** | 2.001 |
| Change a relevant historical main subject | 50 | 1 | **.0009** | 2.000 |
| Change a narrative place (no-effect control) | 192 | 0 | .0165 | .033 |

The model correctly ignores an irrelevant place but also ignores both variables that determine the count. On the same panel it achieves **50.2%** object-place question accuracy but fails that query-object edit as well (L1 **2.009**). The count task is a valid exact-oracle diagnostic but not yet a competent learned circuit.

The matched **no-extra-count** model has **45.9%** count accuracy and **.877** nats CE on the same held-out panel, versus **52.1%** and **.760** with count supervision. Yet its query-person edit TV is **.030**, compared with only **.001** in the count-supervised model (oracle **1**). Historical-subject edit TV is **.012** versus **.0009**. Extra supervision shifts the answer toward **one**: one-count accuracy rises from **64.7%** to **91.2%**, while two-or-more accuracy falls from **25.0%** to **8.7%**. The nuisance-place effect becomes smaller (**.121** to **.033** L1). Thus the label improves aggregate prediction and invariance to an irrelevant field while making relevant-key sensitivity worse. The count-specific sweep stops here; neither checkpoint supports interpreting a learned counting algorithm.

A first-layer attention-output bond check reinforces that distinction. Fitting activation PCA on **narrative-only** data and testing the full joint stream, both its 16/64-direction truncation and a weight-only SVD truncation preserve the model's count-answer distribution almost exactly (model-to-truncated KL **.00016** and **.000006** on 33 count slots). Full-width orthogonal rotations reproduce the untruncated logits within **3e-4**. Yet the untruncated model's count oracle KL on this panel is **.717**, and its causal edits show no counting. Faithful compression of the model is therefore easy here precisely because the model's answer is a simple shortcut; neither basis is evidence of a counting feature. `bond_gauges_layer0_noquestionfit.json` records the other widths and prediction sites.

Prediction, causal fidelity, and local bond compression remain separate measurements. A count-answer feature should only be interpreted if the model responds to the name and relevant subject history while ignoring the nuisance place. The broader project still needs richer syntax and document types, a manually annotated natural-language dependency panel, and whole-task holdouts for shared-dictionary/block-sparse featurizer comparisons.
